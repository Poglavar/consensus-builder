# Consensus Builder responsiveness audit

Start with design search and plan selection. Search stalls when the workspace fills up, and a slow plan request can put the wrong neighbourhood on the map. The next priorities are first load, Plan stats and dense map rendering.

## 1. Make searching and selecting plans cheap and reliable

| Interaction | Observed on Alatau | Proposed change |
| --- | --- | --- |
| Search Designs with Courtyard imported | One input event serialized local design records **28,815 times**. There were 255 published rows and 113 local designs. The memoized identifier check still serializes the whole record on every lookup. | Build one map from content identifier (CID) to local design before joining the two lists. Reuse it across search edits and invalidate it on record changes. Keep the preference for an applied copy when several local records have the same CID. |
| Clear search | The populated list rebuilt 368 cards and 6,340 descendant elements. On a phone-width viewport even the empty workspace rebuilt 4,080 descendants for 255 cards. | Keep card elements keyed by record and update the changed rows. Render a first page and let people reach every result through search, keyboard navigation and pagination. Preserve timestamp order, selection, focused controls and open disclosures. |
| Select Courtyard, then Garden streets while Courtyard is loading | Garden stayed selected. Its 89 designs appeared, then the late Courtyard response drew 113 designs under Garden’s selection. While waiting, the selected card had no spinner and the list status still said “Shown: 8”. | Give each selection a request identifier, capture the selected row before awaiting, and check it before painting. When closing the list opens the selected plan’s inspector, pass that selection through and discard pending map previews. Keep the card mounted, show a spinner while its preview is pending and retain keyboard focus. |
| Switch to Agreements | The tab dropped its busy state while the list still said “Loading…”. The agreements and property-offers reads ran one after the other. | Return the load promise through the tab’s existing busy helper. Start the two independent reads together and display each result as it lands. Track each feed’s pagination and error state independently. |

All six runs displayed identical text and ordering for the 36 matching rows. The experiment left the existing card renderer in place. ## 2. Reduce the work before the first usable map

The staged production build already reduces 524 classic script entries to 101. On a cold English Alatau visit, 111 same-origin JavaScript resources, 67 stylesheets and the English dictionary had finished by app readiness. Their bodies totalled **8.91 MB decoded, 2.58 MB compressed**. At 390 px wide on loopback, two runs reached readiness in 0.31 and 0.40 s. At 10 Mbit/s with 80 ms emulated latency, the same build took **4.44 and 4.46 s**. These are cold HTTP/1.1 measurements. Production uses an edge cache and immutable hashed JavaScript bundles. [Boot script and stylesheet lists](../frontend/index.html#L98) · [Readiness gate](../frontend/js/map-core.js#L1045) · [Production bundler](../frontend/build-static.cjs#L252) · [Production cache rules](../backend/nginx/urbangametheory.xyz.nginx.conf#L258)

Keep map controls, city configuration, relevant language strings and the active workspace on the first-load path. Move road authoring, building-block editing, critics and their styles behind their entry points, using the existing optional-tool loader. Road drawing alone arrived as 266 kB of JavaScript on the untouched 2D map. Bundle the essential CSS and give the remaining stylesheet and dictionary files content-derived URLs. Both currently use a version parameter that falls outside the origin’s immutable-cache rule. A first feature click may wait for its bundle. Show its control as busy immediately and share the first request among callers. [Road loader](../frontend/js/road-drawing-loader.js#L9) · [Optional tools](../frontend/js/optional-tools-loader.js#L51) · [Language loading](../frontend/js/i18n-loader.js#L23)

Two entrances offer smaller, independent fixes.

- **A compact public plan link booted two documents and fetched the same plan twice.** It learns the saved city and camera after boot, then navigates again. Resolve the verified plan in a small route bootstrap, merge explicit URL overrides, choose the workspace and pass that same record to the app. Update the address in place. One navigation and one plan read should suffice even for a saved 3D camera. [Plan arrival](../frontend/js/named-plans.js#L79) · [Saved-view URL rules](../frontend/js/named-plans.js#L9)
- **The globe waits for Three.js before starting an independent coverage download.** Its 1.59 MB decoded coverage file started at 1.21 s, after Three.js core finished. Start both reads together when the globe is requested. Give the globe a Three.js core entry point and let model view request the model loader and controls it needs. Model mode already loads on demand. In Alatau, first model entry requested 64 scripts and took 1.69 s to finish switching. Second entry requested zero scripts and took 0.09 s. ## 3. Show plan figures early and reuse the work behind them

**The published 113-design Courtyard plan took 2.65 s from invoking Plan stats to showing its first figures.** A 479 ms browser main-thread task fell in that interval. The dialog is created after plan preparation. Ground classification and apartment layouts already fill in later. Compare goes further and waits for preparation **and** ground for each selected plan in sequence before opening the dialog. [Plan stats](../frontend/js/proposals/plan-stats.js#L741) · [Comparison preparation](../frontend/js/proposals/plan-stats.js#L864) · [Comparison dialog opening](../frontend/js/proposals/plan-stats.js#L1064)

Open the dialog with the plan titles on click. Show exact member counts and authored figures as soon as their inputs are ready. Mark ground-dependent figures and apartments as pending individually. Start comparison columns with bounded concurrency and keep each in the user’s chosen position. Attach cancellation to the dialog before starting preparation. A slow older selection must never overwrite a newer one. Share verified member data by exact plan revision. Reuse ground results only with the corresponding parcel source, source revision or freshness policy, and local declarations. Move the measured geometry work to a worker or yield between bounded pieces after removing repeated lookups. Each number should retain its present meaning. [Plan preparation and land union](../frontend/js/plan-analysis.js#L95) · [Isolated parcel replay](../frontend/js/agreement-headless.js#L9) · [Existing apartment-layout cache and time slicing](../frontend/js/proposals/plan-units.js#L79)

**Imported Courtyard also exposes a correctness defect.** Importing the editable file and opening Plan stats from its row returned “Cadastral replacement scope cannot be empty.” While preparing that read the browser scanned the local store 113 times and calculated 6,441 design CIDs. The importer initializes each design’s parcel IDs to an empty array. Analysis treats that array as a parcel declaration and discards the surveyed binding it has just resolved. Index declarations once. Distinguish an imported member awaiting binding from an authored declaration of open ground, and use the verified source binding for the former. Cover both cases and compare the imported and published plans’ corresponding ground figures. [Portable import](../frontend/js/plan-file.js#L264) · [Choice of parcel IDs](../frontend/js/plan-analysis.js#L99) · [Local declaration lookup](../frontend/js/plan-analysis.js#L174)

**Private Apply has a network waterfall.** Applying a private plan from its panel awaits one binding POST per member before replay starts. The 113-member demo therefore takes 113 sequential binding calls on that path. Private draft links issue those calls six at a time. Analysis already groups provider-backed members into one browser binding operation per source. Reuse that source-aware preparation in both paths, with a bounded queue for server-backed sources, source-specific request sizes, cancellation and completed-member progress. Keep formation replay ordered and the map commit atomic. This finding comes from the call paths. Live Apply latency was outside the benchmark. [Private plan Apply](../frontend/js/plan-workspace.js#L111) · [Draft link binding](../frontend/js/draft-preview.js#L50) · [Grouped binding](../frontend/js/plan-analysis.js#L18)

## 4. Keep dense map movement and editing within a frame budget

**Each newly arrived building cell triggers a scan of all loaded footprints.** From 45.8116° N, 15.9786° E at zoom 18, an eastward pan added cells containing 662 and 758 buildings. Their arrivals reprocessed 2,322 and 3,080 footprints respectively, spending 46 and 58 ms in reconciliation alone. Only the new buildings changed. Panning back produced zero additional building reconciliations. Propagate changed and evicted IDs from the cell merge, reconcile those IDs, and combine cell arrivals once per animation frame. Draw a large batch in slices if needed. Source changes, building cuts and display-style changes still need their own invalidation. [Cell merge](../frontend/js/map-core.js#L345) · [Repaint scheduling](../frontend/js/map-core.js#L418) · [Signature and layer reconciliation](../frontend/js/map-core.js#L692)

## How to judge the fixes

Use the two Alatau plans, an empty and a populated workspace, and the dense cadastral viewport above as repeatable workloads. For each change, compare identical searches, member and parcel counts, camera state and network settings. The first regression checks should be one local design scan per revision, a delayed first selection losing to the second, a stats dialog that can be closed while ground is pending, one document per compact link and building processing proportional to the changed cell. Aim for local search feedback within 100 ms, a painted busy state on the next frame, and no main-thread task over 50 ms attributable to list joining or footprint reconciliation in these scenarios.

The browser measurements used headless desktop Chrome, fresh profiles, the branch’s production bundle layout served locally, and real public data. The phone scenario used a 390 px viewport on the same computer. On the eight-core host, one-minute load was 4.0–4.2 for the cold-start comparison, 6.1 for the index experiment, 5.1–5.2 for imported-plan stats, 2.5 for published-plan stats and critics, 2.6–3.1 for the narrow list, 4.6–4.9 for the dense pan, 4.0–4.1 for the globe and 3.2–4.3 for the 3D switch. Production-user percentiles, physical-phone frame rates in Photo mode, database query timings and wallet confirmation times require separate measurements.
